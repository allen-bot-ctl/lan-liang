# 栏量 0.4.1 契约：修正会话状态判断（Antigravity、Codex 新对话）

需求：老板 Mac 实测 0.4.0。Antigravity 一轮跑了 40 秒仍显示空闲，做到一半又显示「刚完成」。范围以 PM 04:19 NY、04:21 NY 决定为准。基线 master 0528c47（最新 tag v0.4.0）。没有界面变化，不出样稿；颜色、文案、面板、菜单栏小点、优先级、超时都和 0.4.0 一样。

## 0.4.0 错在哪里
0.4.0 合同假设 Antigravity 会先写一行 status=RUNNING，做完再写 DONE，所以用 RUNNING 判断工作中，用 DONE 加 5 秒去抖判断刚完成。
这个假设是错的：transcript.jsonl 是**每一步做完才写一行**。老板 Mac 上一个 50 行的文件里，49 行是 DONE，只有 1 行是 RUNNING。结果是：
- 一轮正在跑，却几乎看不到 RUNNING，所以显示空闲；
- 每写一行 DONE 就重新进入一次「刚完成」，所以做到一半就变绿。

根本原因是 mind 写合同前没有先用真实日志核对，只凭第三方代码和字段名推断。以后凡是按日志判断状态的合同，先要有一段老板 Mac 上的真实序列（只要类型和时间，不要正文），再定规则。

## 0.4.0 作废的条目（以本合同为准）
- §1.2 Antigravity 映射表全部：RUNNING → 工作中、DONE → 刚完成（含 5 秒去抖，PM 03:10 NY 同意的那条）、ERROR → 出错、USER_INPUT 忽略。
- §1.2「去抖的理由」一段。
- §1.2「只取顶层 status 字段」：改为本合同 §A1 列的字段。
- §1.3 启动时恢复状态里 Antigravity 的部分（「最后一条认识的事件是工作中」）：改为本合同 §A3。
- §1.3「只对含 `"status"` 字样的行做 JSON 解析」（Antigravity 部分）：改为对所有不超过 64KB 的行解析。
- §4「Antigravity 的 USER_INPUT 忽略」。
- §5 A2 单测；B4 自检序列里的 RUNNING、DONE、ERROR 三步；C4 实测步骤。
- §1.3 Codex「新出现的文件：超过 64KB 时只读末尾 64KB」：改为本合同 §B1。

其余 0.4.0 条文不变，包括：10 分钟无新行退回空闲、刚完成/出错 60 秒后消失、优先级、颜色、FSEvents、不读正文、不注册钩子、不读 language server 令牌、启动只看 transcript.jsonl 自己的 mtime（PM 03:53 NY）。

## A. Antigravity

### 现场证据（PM 04:18 NY 在老板 Mac 上只读核对）
- 文件：`brain/<id>/.system_generated/logs/transcript.jsonl`。
- 一行里有这些字段：type、status、source、created_at、step_index。PLANNER_RESPONSE 另有 tool_calls、model、token 计数等。
- type 有：USER_INPUT（source 为 USER_EXPLICIT）、PLANNER_RESPONSE、GENERIC、SYSTEM_MESSAGE、ERROR_MESSAGE、CHECKPOINT。
- 一轮里每做完一步写一行。最终回复是一行**不带 tool_calls** 的 PLANNER_RESPONSE。
- 一轮里相邻两行最长隔 17 秒。
- coder 用老板全部会话核对：不带 tool_calls 的 PLANNER_RESPONSE 之后，下一条
  - 352 次是 USER_INPUT；
  - 136 次是 source 为 SYSTEM 的 SYSTEM_MESSAGE 或 ERROR_MESSAGE，隔 4 秒到 30 分钟才来，这是后台任务唤醒 agent 接着干。

### A1. 读哪些字段
- 只取 `type`、`status`、`source`、`created_at`，以及 `tool_calls` 这个键**是否存在且非空**。
- 不取 tool_calls 的内容，也不取 model、token 计数、正文等其他字段。这些不存、不进日志。
- 只认文件名正好是 `transcript.jsonl` 的文件，位置同 0.4.0。

### A2. 每一行怎么判断（从上往下，命中第一条就停）

| 这一行 | 会话状态 |
|---|---|
| `type == "ERROR_MESSAGE"`（不管 status），或 `status == "ERROR"` | 出错（**待 PM 确认**） |
| `type == "PLANNER_RESPONSE"` 且没有 `tool_calls` 键或它为空，或者 `type == "CHECKPOINT"`（下称「结束记录」） | **立即**刚完成，不等待、不去抖（**待 PM 确认**：不等 30 秒） |
| 其他任何能解析的行，包括 USER_INPUT，source 为 MODEL 或 SYSTEM 的行，GENERIC、SYSTEM_MESSAGE、带 tool_calls 的 PLANNER_RESPONSE | 工作中 |
| 解析不了的行（坏 JSON、没有 type） | 状态不变，但算作「有新行」，重置 10 分钟计时 |
| 超过 64KB 的行（不解析） | 工作中（这种行通常是带大量 tool_calls 的步骤） |

- 不再用 status 的 RUNNING、DONE 判断状态。
- 刚完成之后，再来 USER_INPUT，或者 source 为 MODEL/SYSTEM 的任何新行，都立刻回到工作中。比如后台任务唤醒时写的 SYSTEM_MESSAGE。
- 出错之后再来新行，同样按上表走。
- 工作中的起点：这一轮第一行「工作中」的 `created_at`，取不到时用文件 mtime。

### A3. 栏量启动时（只读末尾 64KB，末尾里可能没有 USER_INPUT）
只看文件 mtime 在 10 分钟内的 transcript.jsonl，取末尾 64KB 里最后一条能解析的行：
- 最后一行是结束记录，且文件 mtime 在 60 秒内：刚完成，按 mtime 起算，满 60 秒消失。
- 最后一行是出错行：空闲，启动前的出错不补显示。
- 其他行：工作中，时长从文件 mtime 算起（0.4.0 已接受的已知行为，PM 03:53 NY）。
- 文件 mtime 超过 10 分钟：空闲。

### A4. 兜底
- 用户中途打断时，不会写最终回复，就靠 0.4.0 的规则：10 分钟没有新行，退回空闲。
- 本版不为「打断」单独做状态。

## B. Codex

### B1. 启动后才出现的会话文件，从头读
- 栏量启动后才新出现的 rollout 文件（FSEvents 报新建，或者启动时不在已知列表里），从文件开头读，只解析状态事件。
  - 一次最多读 1MB 的上限不变，超出部分下次接着读。
  - 单行超过 64KB 不解析的规则不变。
- 启动时已经存在的文件，仍然只读末尾 64KB。
- 启动时只看今天和昨天两个日期目录，这条不变。
- 原因：ChatGPT.app 里 Codex 桌面版新开对话时，文件开头很大，`task_started` 在第 28KB 处；约 4 秒后又一次写入约 115KB。按 0.4.0 的做法，第一次只读末尾 64KB 会漏掉 task_started，这一轮就一直认不出工作中。
- 不在范围内：ChatGPT 普通对话在云端，本机不写日志，栏量看不到，也不显示。

## C. 自检
- `--debug-agent-status` 打印结果（`DEBUG_AGENT_STATUS ok` 或 `failed`）后，进程自己退出。ok 退出码 0，failed 退出码非 0。
- 自检序列里的 Antigravity 部分换成 §D 的真实序列 fixture，外加「刚完成 → SYSTEM_MESSAGE → 工作中」和「ERROR_MESSAGE → 出错」两步。

## D. 验收

### 单测
fixture 放在 `fixtures/agent-status/`。每行只保留 type、status、source、有没有 tool_calls（写成 `"tool_calls":[{}]` 或不写）、created_at、step_index，不带正文。

1. **真实序列**：照老板 Mac 上 09:15:04–09:18:40 那段，step 20–49，created_at 用 UTC，status 除第 23 步外都是 DONE。逐行断言：
   - step 20–31：工作中（中间 09:15:08→09:15:25 停 17 秒，不能变空闲或刚完成）；
   - step 32（不带 tool_calls 的 PLANNER_RESPONSE）：刚完成；
   - step 33（USER_INPUT）：立刻回到工作中；
   - step 34–49：一直是工作中，中间不出现刚完成。
2. **做到一半启动栏量**：文件只保留 step 35–49，没有 USER_INPUT，mtime 设为 10 秒前，启动应为工作中。同一文件 mtime 设为 11 分钟前，应为空闲。
3. **启动时最后一行是结束记录**：mtime 30 秒前为刚完成，30 秒后消失；mtime 90 秒前为空闲。
4. **刚完成后被唤醒**：最终回复之后隔 4 秒来一行 source=SYSTEM 的 SYSTEM_MESSAGE，回到工作中；隔 30 分钟再来也一样。
5. **出错**：type=ERROR_MESSAGE 且 status=DONE，判为出错；status=ERROR 且 type 为 GENERIC，也判为出错；60 秒后消失。
6. **CHECKPOINT**：判为刚完成。
7. **tool_calls 为空数组**的 PLANNER_RESPONSE：判为刚完成。
8. **中途打断**：最后一行带 tool_calls，之后 10 分钟没有新行，判为空闲；第 9 分 59 秒来一行，仍是工作中。
9. **不读正文**：fixture 的 tool_calls 和一个额外字段里放标记串，断言它不进内存结构和日志。
10. **Codex 新对话**：启动后新建一个 rollout 文件，先写 28KB，其中含 task_started；4 秒后再写 115KB，没有新的状态事件。应认出工作中，且不因为第二次写入而丢失。
11. **Codex 启动时已存在的文件**：只读末尾 64KB（0.4.0 的 A9 照旧通过）。
12. 0.4.0 及更早的单测全绿（0.4.0 的 A2 按本合同替换）。

1. Antigravity 发一个要跑 1 分钟以上、中间会停顿的任务：全程蓝点；最终回复出来后才变绿；绿点 1 分钟后消失。

4. 退出再打开栏量，额度 ≤ 3 秒出现（沿用 0.1.5 验收 8）。
