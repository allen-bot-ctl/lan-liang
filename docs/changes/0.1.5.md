# 栏量 LanLiang v0.1.5 契约（mind，2026-11-24 23:1x NY，范围以 PM 23:04 NY 为准）

三件事，其余同 0.1.4：
1. Gemini 用量解析提速（只解出时间和用量）；
2. 统计结果存到 `~/.lanliang`，重启后马上出图；
3. 纵轴刻度满 1000 万时去掉小数。

背景：0.1.4 没有磁盘缓存，每次启动都要复制约 190MB 对话库，并完整解码每条记录，老板实测首次出数约 40 秒。

## 1. 解析提速
- 动手前，先在老板 Mac 上实测一次 0.1.4 的首次扫描，分成复制、SQLite 读取、解码三段计时，在群里报数字。改完后，按同样三段再报一次。
- SQL 只取需要的列：`SELECT metadata FROM steps`。退回 gen_metadata 时只取 `data`。不取其他列，也不 `SELECT *`。
- 解码器只认 `metadata` 里的字段 1（时间）和字段 9（用量消息），其余字段直接按 wire type 跳过：不拷贝、不建对象、不递归解析。用量消息里只取子字段 2、3、4、5、9、10。gen_metadata 只取字段 1 下的字段 4 和字段 20（取时间用），其余同样跳过。
- 复制规则、数据源目录、去重和统计口径都和 0.1.4 完全一致，统计结果必须与 0.1.4 逐日相同。
- 只有变过的对话才复制和重读，判断方法见第 2 节。

## 2. 磁盘缓存
- 文件：`~/.lanliang/gemini-usage-cache.json`，目录 700、文件 600。先写同目录临时文件，再 rename 覆盖（原子写入，与 0.1.3 的令牌缓存同一写法）。
- 内容：`{"version": 1, "entries": {"<db 绝对路径>": {"dbSize", "dbMtime", "walSize", "walMtime", "days": {"yyyy-MM-dd": tokens}}}}`。没有 -wal 时，walSize 和 walMtime 记为 0。
- 启动时先读缓存，立即用缓存画图，再在后台扫描：
  - 四个值全没变的对话直接用缓存，不复制、不打开；
  - 变了的和新出现的对话才复制重读；
  - 已经不在目录里的对话从缓存删掉。
  - 扫描完写回缓存，只有内容变了才写。
- 读取失败的对话不写进缓存，下次扫描重试，仍计入「· N 个对话读取失败」。
- 缓存读不了、version 不是 1、JSON 坏了，都当作没有缓存，从头扫描后覆盖写，不弹错误、不报失败。
- 缓存里只有日期和数字，不存对话内容、文件名以外的任何文本、令牌。
- 不写 `~/.gemini`，不写钥匙串。

## 3. 纵轴刻度
- 用量图纵轴刻度：≥1 亿时用「x.xx亿」（同现在）；≥1000 万且 <1 亿时不带小数，如「4450万」；<1000 万时同现在。
- 悬停气泡里的数字、Codex 的气泡和数字格式都不变。
- 刻度字号恢复到和 Codex 一样，不再因为太长被缩小。

## 4. 首次扫描期间
- 没有缓存时，图的位置显示「正在统计…」（同 0.1.4）。额度区、页签切换和菜单栏照常响应，不能等扫描。
- 有缓存时，不显示「正在统计…」，直接画缓存里的图，扫描完无感更新。

## 不做
- 不改数据源、口径、展示样式（刻度除外）、文案。
- 不加进度条，不加设置项。

## 验收
0. 群里有 coder 在老板 Mac 上的前后对比数字：复制、SQLite 读取、解码三段，以及总用时。
1. 性能（老板 Mac，约 190MB）：无缓存首次扫描 ≤5 秒；有缓存时，启动后 ≤1 秒出图。
2. 单测：同一组合成库，0.1.4 的结果和 0.1.5 的结果逐日相同。
3. 单测：有缓存且文件都没变时，复制和打开次数为 0；改一个库只重读那一个；删掉的库从缓存和结果里消失；读取失败的库不进缓存。
4. 单测：缓存文件坏 JSON、version 不对、文件不存在时，都从头扫描且结果正确；写入后文件权限 600、目录 700。
5. 单测：刻度格式 9_990_000 → 「999.00万」，10_000_000 → 「1000万」，44_500_000 → 「4450万」，335_000_000 → 「3.35亿」；悬停格式不变。
6. CI 截图：Gemini 有数据（每日，悬停一根柱子），浅色、深色各一张，刻度为「xxxx万」且字号与 Codex 一致；Codex 页签与 0.1.4 一致。
7. 0.1.4 及更早的测试全绿，不回归。

## 5. 额度先出、Codex 本机扫描增量化（PM 23:16 NY 补充决定，coder 实测定位）
背景：老板 Mac 上 `~/.codex/sessions` 有 2.7GB（29 个 jsonl）。0.1.4 刷新时先把这些文件全部读进来逐行解析（只有内存缓存，每次启动全量重读），读完才发额度请求，而且额度要等 Codex 和 Gemini 都完成才一起显示。实测重启后菜单栏一直显示「…」，约 90 秒才出数。Gemini 历史扫描只占 1～2 秒。

1. Codex 本机扫描移出额度路径：额度请求不等本机扫描，请求一回来就更新菜单栏和额度区，用量图后到。图还没出来时，Codex 页签图的位置显示「正在统计…」（与 Gemini 同一文案和样式）。
2. Codex 和 Gemini 额度各自到了就各自显示，不互相等。菜单栏两行里，先到的那行先变成数字，另一行保持「…」。
3. Codex 扫描结果写磁盘缓存 `~/.lanliang/codex-usage-cache.json`，规则同第 2 节的 Gemini 缓存：目录 700、文件 600、原子写入、`version: 1`，读不了就当没有缓存。每个 jsonl 记录：绝对路径、文件 inode、大小、修改时间、已读到的字节偏移、按日 token 字典。
   - 增量读：文件变大且 inode 没变时，只从偏移处读新增部分。只处理到最后一个换行符为止，没写完的半行留给下次。偏移推进到最后一个换行之后。
   - 文件变小、inode 变了（被替换）、缓存坏了，都把这个文件从头重读。
   - 文件没变就不打开。不在目录里的文件从缓存删掉。
   - 统计口径和 0.1.4 完全一致，增量结果必须与全量重读逐日相同。
4. 扫描优先级：Codex 和 Gemini 的本机扫描都放在后台队列，qos 为 `.userInitiated`（PM 23:12 NY 决定；`.utility` 下实测 SQLite 读取慢 10 倍以上）。主线程只接收结果。

追加验收：
8. 老板 Mac 退出栏量再打开，菜单栏额度 ≤3 秒出现（Codex 和 Gemini 两行都要有数字）。
9. 单测：Codex 增量读和全量读结果逐日相同；在文件末尾追加完整行只读新增部分（断言读取字节数）；末尾半行这次不计、补全后下次计入；文件变小或 inode 变化时整份重读；缓存坏 JSON 时从头读。
10. 单测或 UI 测试：本机扫描人为延迟 10 秒时，额度仍在网络返回后立即显示；一个服务的额度请求卡住时，另一个服务照常显示。
